# Memory & retrieval design

> Part of `docs/ai/` — git-tracked, public. Code-architecture facts only. See
> `architecture.md` for the exposure rule this doc set follows.

## Chat flow

`_run` in `chat_service.py`: fetch session → `retrieval.retrieve()` finds keyword/always-on lore matches against the recent text → `memory_service.retrieve_block()` embeds the query, calls `lore_memory.fetch_lore_candidates()` (keyword matches + semantic KNN lore hits + one-hop `lore_links` relationship expansion, session overrides applied) and merges those lore candidates with typed memory facts (`memory_facts.similar_live` KNN + `memory_facts.reserved()` pinned/active state facts) into one ranked, token-budgeted block (`memory_ranking.rank()` + `memory_block.build_block()`) → `build_system` → call `llm.chat_stream` → stream SSE deltas to client → persist message → `memory_service.maybe_extract()` batches settled exchanges into `extract_batch()`, which runs typed-fact extraction, folds `doing`/`location`/`known_names` into the session's char-state, reconciles drafts against existing facts, and calls `lore_memory.detect_and_apply_lore_updates()` to turn any detected story-canon changes into session-scoped lore overrides.

Regeneration/group-reassign pops the trailing assistant message and, if that exchange's batch was already extracted, `memory_service.rollback_discarded_turn()` deletes every fact tagged with that batch's `batch_id`, restores any fact those deletions had superseded (clears `valid_until_turn`/`superseded_by`), and rewinds the extraction cursor (`memory_extract_cursors`/`memory_extract_batches`) to the batch's start so the next `maybe_extract()` call re-extracts it fresh against the regenerated content — no ghost facts survive a swipe. Rollback operates at whole-batch granularity (`BATCH_SIZE=5` exchanges bundled into one extraction call), since drafts aren't attributed back to a single exchange within a batch — invalidating one regenerated exchange re-derives facts for its unregenerated batch-mates too, which is safe (same content in, same facts out) but not free. Reinforcements applied by the discarded batch (a `reinforce` decision bumping an existing fact's `reinforcements`/`last_turn` in place, not a new row) are reversed exactly: every `reinforce` records the fact's prior `reinforcements`/`last_turn` under its `batch_id` in `memory_reinforce_log`, and rollback restores each affected fact to the earliest prior value among the rolled-back batches (`_restore_reinforcements`), so a surviving fact's counters land exactly where they'd be had the discarded turn never happened — no skew. `known_names` on the session is append-only by design and is not pruned on rollback, so a name introduced only by discarded content can linger (harmless, matches the existing char-state philosophy).

## Memory scoping

Memory facts (`backend/repositories/memory_facts.py`) are stored per `session_id`, never cross-session — `similar_live`/`reserved`/`list_live` all filter on it. A fact superseded by a newer draft (`supersede()`) gets `valid_until_turn`/`superseded_by` set rather than being deleted, so history remains reconstructable; `reinforce()` just bumps a reinforcement counter and `last_turn` in place. Memory/lore/character-state text is stored in whatever language the session was using at the time — it isn't retranslated if the session's language changes later.

## Memory (typed-fact system)

`backend/memory_service.py` / `backend/memory_extraction.py` / `backend/memory_ranking.py` / `backend/memory_block.py` / `backend/lore_memory.py`, unconditional — no flag, no legacy parallel path. Typed facts (`event`/`state`/`relationship`/`world`/`profile`) are extracted in batches of 5 settled exchanges (`memory_service.maybe_extract`/`extract_batch`, `BATCH_SIZE` in `memory_service.py`) via `memory_extraction.run_extract`, which also returns a `char_state` (doing/location/npcs) folded directly into `chat_sessions.set_char_state` — the char-state tracking the old legacy `remember()` used to own now lives in this same extraction call, not a separate system.

Drafts are then reconciled against nearest-neighbor existing facts (`run_reconcile`) into `add`/`reinforce`/`supersede` decisions — a fully-failed reconcile-parse falls back to treating every draft as a new `add`, with no downstream dedup safety net. The same batch of drafts is also passed to `lore_memory.detect_and_apply_lore_updates()`, which searches each draft's nearest lore neighbors and asks `memory_extraction.run_lore_update_detection` whether the story just changed established lore; an applied decision calls `lore_memory.apply_session_lore_override()`, writing a pinned `state` fact and recording it in `session_lore_state` so retrieval always resolves that lore entry to the override going forward.

Retrieval (`memory_service.retrieve_block`) does KNN candidate search over both memory facts and lore (`lore_memory.fetch_lore_candidates`), then `memory_ranking.rank()` applies decay-weighted retention scoring (reinforcements/importance/valence, filtered by whether mentioned participants are actually present in the recent text — the closest thing this system has to POV filtering) to the non-pinned candidates from both sources, then `memory_block.build_block()` packs pinned/active/ranked facts and lore into a single token budget (`memory_v2_budget_tokens`, code default 1000 — the live value in a given deployment's `settings` table can differ significantly, so check it before reasoning about what fits), split 60% reserved / 40% scored.

Facts persist in `backend/repositories/memory_facts.py`; `purge_session()` is called from the session-delete endpoint (`backend/routers/sessions.py`), so deleting a session removes its typed facts and extraction cursor row. This whole system — including the session-lore integration below — has direct test coverage on the extraction/ranking/packing logic itself (`test_memory_extraction.py`, `test_memory_ranking.py`, `test_memory_block.py`, `test_memory_service.py`, `test_lore_memory.py`, `test_memory_lore_integration.py`), in addition to the DB-facing repository layer (`backend/tests/test_memory_facts_repo.py`).

## Session-scoped lore overrides

`backend/routers/session_lore.py`, a router distinct from `backend/routers/lore.py`: lets a session pin a per-session override of a lore entry's effective content, and tracks per-secret reveal state (which of a lore entry's hidden `lore_secrets` have been revealed in *this* session specifically) without mutating the shared entry other sessions/characters see. An override can be set explicitly by the player (`PUT /sessions/{sid}/lore/{lid}/override`, delegating to `lore_memory.apply_session_lore_override`) or proposed automatically by the extraction pipeline's lore-update detection described above — both paths converge on the same `session_lore_state` override + pinned memory fact. Both a reveal and an override write directly into the memory fact store as a side effect — a reveal inserts an `event` fact, an override inserts/updates a `pinned` `state` fact.

## Lore retrieval

Keyword-triggered plus semantic KNN. `retrieval.retrieve` matches always-on entries, then entries named in the **current turn's text**, then entries matching the wider recent-text window, then runs bounded recursion over matched entries' content (`LORE_RECURSION_MAX_DEPTH` passes, at most `LORE_RECURSION_MAX_ADDED` entries added). Entries matched in the current turn carry `query_matched` through to their candidates and sort ahead of importance in `lore_memory.fetch_lore_candidates`, so an entry the player just named always wins a pinned slot rather than losing it to a stale higher-importance match. Lore content lives in the relational `lore` table; `lore_vectors` stores only the lore id + vector. KNN hits are resolved back to content via `db.lore_by_ids`. `lore.update()` deletes a lore entry's secrets when its content changes but does not re-run `index_lore()` itself — re-embedding is the router's responsibility (`routers/lore.py`), not enforced at the repository level, so a direct repository-level caller that skips the router leaves a stale embedding. The retrieval merge logic (`retrieval.retrieve`) and embed-text construction (`index_lore`) are covered by `test_retrieval.py`, in addition to the repository CRUD/linking/secrets layer (`test_lore_repo.py`, `test_lore_links_repo.py`, `test_lore_secrets_repo.py`).

## Lore-to-persona conversion

`become_persona_from_lore` (`routers/lore.py`) lets an owner turn a Character-category lore entry into a playable persona other users can select — permission-gated (blocks conversion of hidden entries for non-owners) and tested, but otherwise undocumented feature surface worth knowing about when touching either the lore or persona subsystems.
