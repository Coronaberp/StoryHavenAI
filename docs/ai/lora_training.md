# Image generation & LoRA training

> Part of `docs/ai/` — git-tracked, public. Code-architecture facts only. See
> `architecture.md` for the exposure rule this doc set follows. Live operational detail
> (dashboard names, restart/runbook steps) intentionally stays in the gitignored CLAUDE.md.

## Image generation (ComfyUI)

`imagegen.py` submits/polls ComfyUI workflow graphs (txt2img, img2img via reference image, upscale) and lists installed checkpoints/LoRAs/samplers/schedulers/upscalers by querying ComfyUI's own node option lists — there is no local model registry, ComfyUI is the source of truth. **Model requests** (`model_requests` table, `routers/sessions.py` submit + `routers/admin.py` approve) are deliberately never auto-downloaded server-side: `source_url` is only checked against an admin-configured host allowlist (`CFG['model_request_hosts']`), never fetched — approving a request just lets the admin copy a generated download-and-fix-ownership command to run manually against ComfyUI's model volume. This is intentional (see `_match_model_request_host`'s docstring) — fetching an arbitrary user-submitted URL server-side is an SSRF risk the app avoids entirely rather than mitigates.

## LoRA training (Modal)

`POST /admin/lora-training/jobs` returns `{"job_id"}` immediately — training runs as a fully decoupled `asyncio.create_task` (`_execute_training_job`), not tied to the request/SSE connection, so a closed tab or dropped connection never stops a run. The browser only ever polls `GET .../jobs` (see `static/js/lora-training.js`'s `TrainingJobWatcher` class); progress/log/metrics are persisted to the DB (`lora_training_jobs.metrics`, a JSON column) on every event, so a page reload just resumes polling the same state. Only one job actually trains at a time (`_training_queue`, a rented GPU is billed per job) — every other queued job's `log` shows how many jobs are ahead of it until it reaches the front.

`POST .../{jid}/abort` does three things, all immediately, not just cooperatively: adds the job id to `_aborted_jobs`, calls `_queue_leave` to free its queue slot right away (so the next queued job can start instantly rather than waiting for the aborted task to notice), and calls `.cancel()` on the actual `asyncio.Task` via `_running_job_tasks` (a `job_id -> Task` map). That last part matters because `_aborted_jobs` is only checked cooperatively at two points (the queue-wait loop and the Modal SSE streaming loop) — the provisioning/checkpoint-caching phase in between has no such check, and a long-running unbounded call there (a multi-GB upload, deliberately unbounded timeout) would otherwise keep running for real, on Modal's side, with real billing, completely deaf to an abort that only set a flag. `task.cancel()` actually interrupts it at whatever await point it's suspended at.

Base checkpoints/CLIP/VAE and the per-job training image set (with per-image captions) are all uploaded to a Modal `Volume` — `ensure_models_cached`/`upload_dataset_images`/`download_output` (`modal_client.py`) use Modal's own Python SDK (`modal.Volume.batch_upload`/`read_file`/`iterdir`) directly rather than a hand-rolled HTTP endpoint, for both throughput and proper error propagation if Modal kills the receiving side mid-transfer. Every not-yet-cached checkpoint file and every dataset image is put into a single `batch_upload()` session per call rather than one file/request at a time, so Modal transfers them concurrently over multiple streams. `train()` (`modal_app/lora_train.py`) reads the dataset straight from the Volume-mounted dataset path instead of receiving a zip in the training request's own POST body, which stays config-JSON-only. `remove_dataset_images` deletes a job's uploaded dataset once it truly finishes (success, final give-up, or abort) — not per retry attempt, since a retry reuses the same already-uploaded dataset. Finished output (the trained LoRA, and any mid-run checkpoint) lives in the Volume's output subfolder and is removed from there once fetched — job-scoped one-shot handoffs, not reusable cached inputs like the base checkpoints.

A job can resume from an existing (partially-trained or otherwise complete) LoRA instead of starting over: `resume_from_lora` (form field on job creation) uploads that existing `.safetensors` alongside the base checkpoint and passes it to `sd-scripts` as `--network_weights`. This only initializes the network's weights — it does not restore optimizer/momentum state or a persisted step counter — so resuming several times is additive (never undoes earlier learning) but isn't bit-identical to one uninterrupted run. The job's own `resume_from_lora` column and a frontend badge make a resumed run visibly distinct from a fresh one.

`_execute_training_job`'s post-provisioning phase (`_stream_one_attempt`, called in a retry loop) auto-retries a **transient** failure (a dropped stream, Modal's SSE ending without a final `done`/`error` event, an unexpected exception) up to `MAX_AUTO_RETRIES` (3) times, resuming from whatever checkpoint was last saved via the same `resume_from_lora` mechanism above — the job's status goes back to `queued` with a log line explaining the retry rather than failing outright. It does **not** retry: an explicit abort (`_JobAborted`), a Modal-not-configured setup problem, or an error matching a known-unrecoverable pattern (e.g. "checkpoint not found in the model cache" — a config problem that would fail identically on every retry, not worth burning attempts on).

Training quality knobs baked into `modal_app/lora_train.py`'s dataset writer/training command: `enable_bucket` (images of different aspect ratios are grouped into resolution buckets instead of all being force-resized to one square resolution), `shuffle_caption=true` with `keep_tokens=1` (shuffles any tags after the trigger word each epoch while keeping the trigger word pinned first), and `--min_snr_gamma=5.0` (always on, a standard fix for washed-out contrast). `noise_offset`/`network_dropout` are optional, off-by-default form fields passed straight through as the matching `sd-scripts` CLI flags. Per-image captions (typed per-thumbnail, or bulk-imported by matching uploaded `.txt` filenames to image filenames) replace the old flat single-trigger-word-only caption.

The training-progress cost banner (`static/js/lora-training.js`'s `_updateCostBanner`) computes real elapsed time from the timestamp stamped server-side the moment a job leaves `queued` and Modal actually starts doing work, rather than job-submission time — Modal never bills queue wait, so a job sitting behind another one in the queue shows no cost accruing until it's actually running.

If `sd-scripts` goes completely silent (no stdout at all, no exception) for too long, `_stream_subprocess` (`modal_app/lora_train.py`) kills it itself rather than waiting on the training function's multi-hour hard timeout — `_STALL_LIMIT_SETUP` (20 min, generous because VAE/text-encoder latent caching on a large dataset legitimately takes a while) before any step has run, `_STALL_LIMIT_MID_TRAINING` (10 min) once at least one step has completed. This was added after a real run sat frozen mid-training with zero output and zero exception until Modal's own timeout finally killed it — a genuine hang inside the training subprocess itself, not this app's code, but this app is what actually kills it fast now.

If a training job's status still looks stuck/wrong after aborting from the app, the Modal dashboard is the fastest way to check and, worst-case, cancel it by hand — a call already in flight when abort was hit may still show "Running" there until `task.cancel()` actually propagates. (The specific Modal app name to look under lives in CLAUDE.md, not here.)

Every phase of a training run logs a descriptive, single-line entry to the job's persisted `log` field — a silent phase once masked a run that failed and lost its output entirely, burning real GPU spend with no way to diagnose what happened after the fact. `modal_provision.ensure_deployed` auto-deploys the Modal app the first time it's needed and re-deploys if a liveness probe shows the cached deployment died — this also means editing `modal_app/lora_train.py` does **not** auto-redeploy if the current deployment is still alive; a stale deployment can sit there until it goes down on its own. Modal auth and the deploy's own shared secret are infra credentials cached into config, not something to paste manually per call.
