# Roles (RBAC)

> Part of `docs/ai/` — git-tracked, public. Code-architecture facts only. See
> `architecture.md` for the exposure rule this doc set follows.

`users.role` is free-text — `'guest'` | `'member'` | `'admin'` are the seeded built-in roles (`roles` table, `is_builtin=true`), plus whatever custom roles a Dev creates (`POST /admin/rbac/roles`); `'dev'` is never a stored role at all, it's a hardcoded bypass. `is_admin` is derived (`role in ("admin", "dev")`), never a second source of truth.

Access control is capability-based, not a fixed R/W/X matrix: `role_capabilities` (`role`, `capability`) is a pure grant table — a row's presence means the role has that capability, absence means deny (fail-closed). Every gated endpoint declares its own capability once, at the exact dependency call site, as a `(key, description)` pair — `Depends(require_capability("users.suspend", "Suspend or unsuspend a user account."))` — and that call registers the pair into an in-process `CAPABILITY_REGISTRY` dict the first time the module imports, so `GET /admin/rbac/capabilities` (what the Dev-only role editor reads) can never drift out of sync with what the code actually enforces. `require_capability` bypasses entirely for `role == "dev"`. Capability keys are namespaced `noun.verb` (`comments.delete_any`, `system_settings.manage`); the substring before the first `.` doubles as the grouping key in the editor UI.

Ownership is never itself a capability — "delete your own X" is unconditional for every authenticated user; only the *override* ("delete someone else's X") is capability-gated. Where the check lives inside a handler body rather than as a route dependency (e.g. `comments.py`'s `delete_comment`: author check first, `has_capability(role, "comments.delete_any", ...)` as the fallback), that capability must also be registered eagerly at module import time — not only inside the function body — or `seed_defaults()` (which runs at app startup, before any request has ever hit that handler) won't see it in the registry and won't grant it to `admin`. `comments.py` does this with a module-level `CAPABILITY_REGISTRY["comments.delete_any"] = "..."` line right after its imports, kept in addition to (not instead of) the in-body `has_capability` call.

Dev tier is granted via `PUT /admin/users/{uid}/dev-role`, hardcoded to `Depends(get_dev)` — this endpoint, and the whole `backend/routers/rbac.py` role/capability management API itself, stay outside the capability system on purpose (gating RBAC administration through RBAC risks a config error locking every Dev out). A regular admin can never self-escalate to Dev. This is also the one other place besides `admin_update_dev_role` that should stay hardcoded rather than migrated if a future endpoint needs a similar "can only be touched by the literal Dev role, never by a grantable capability" guarantee.

`seed_defaults()` (`backend/repositories/role_capabilities.py`) only ever seeds a role once — gated on a real `roles.capabilities_seeded` marker column, not a row-count heuristic (a role with a single default capability that gets revoked to zero rows must never look identical to "never seeded" and get silently re-granted on the next restart). A capability added by a future code change is therefore *not* automatically retrofitted onto an already-seeded `admin` on an existing deployment — it needs an explicit grant via the RBAC API (or a one-off data migration) the same way a brand-new custom role would. Never reintroduce a hardcoded-username or hardcoded-role check for a privilege decision (the old `if username == "zukaarimoto"` pattern that predated all of this) — always gate on a named capability, or on `role == "dev"` for the handful of things that are deliberately Dev-only forever.
